|---|---|---|

What `xgboost_v2` is: XGBoost with an absolute-error objective trained on the
correction over persistence (the 24 h value is the base margin), using only the
ten leakage-derived 0/24 h features, with a quiet-part gate: a part whose 24 h
level and drift are both within 2 robust standard deviations of its batch keeps
the plain 24 h value (chosen on training folds: healthy-part MAE 0.0128 vs
0.0165; bagging was tried and dropped). v1's XGBoost lost because squared error
inflates healthy forecasts by about 0.12 of the limit; the v2 objective does not.
Details, diagnostics and the predeclared comparison: `docs/CLAUDE_FORECAST_V2_HANDOFF.md`
and `outputs/claude_forecast_v2/`. Codex's independent evaluation of the same
candidate: `outputs/codex_ml_v2_review/` in the main project.

**Interval change.** `xgboost_v2` carries a stratified asymmetric interval
(strata on the 24 h slope robust z, margins from signed residuals on the
calibration batches). `prediction_lower`/`prediction_upper` are each one-sided
90 % bounds, so the pair is an **80 %** interval (`interval_nominal_coverage:
0.8`, `upper_bound_nominal_level: 0.9`); the wider two-sided 90 % pair is in
`prediction_lower_two_sided`/`prediction_upper_two_sided`. On the test batches
the reported pair covered 83.0 % and the upper bound held for 91.9 %. The
decision rule is unchanged: MONITOR when `prediction_upper` reaches the limit,
which now means "about a one-in-ten chance of ending above the limit". Other
models keep the v1 symmetric radius and `interval_nominal_coverage: 0.9`.

**Contract: additive only.** New optional fields on `forecast`:
`interval_stratum`, `upper_bound_nominal_level`, `prediction_lower_two_sided`,
`prediction_upper_two_sided`; on `xgboost_explanation`: `explained_model`
(`xgboost_v2` when it produced the forecast, `xgboost` for the v1 candidate).
`available_models` gains `xgboost_v2`. Schema version stays `1.0.0`.

### Fixed: outcome crossings were hard-coded false

`_evaluation()` set `crossed_applicable_limit=False` on every outcome row
regardless of the reading. On the 240-component sample **7 components genuinely
exceed their limit at 168 h**, and all 7 were reported as `false` — the outcome
reveal, which is the whole point of the demo's payoff, showed that nothing had
failed.

Fixed by taking the limit from the uploaded history (`limits_by_identity()`;
the core's outcome rows carry the reading but not the limit) and comparing
directly. The field is now `bool | None`: `null` means the limit was unknown, so
no comparison was possible, and is documented as *not* meaning "stayed in spec".
`applicable_limit` is returned alongside so the comparison is visible.

Two regression tests derive the expected crossing set independently from the raw
CSV and assert the API reports exactly that set.

### What the reveal now shows, and it is not flattering

With the field working, the 240-component sample says:

| | |
|---|---|
| crossed the limit at 168 h | 7 |
| of those, flagged at 24 h | **4** (3 × RETEST, 1 × MONITOR) |
| missed | **3** — `MLCC_C001055`, `MLCC_C003296`, `MLCC_C003334`, all ACCEPT |
| total flagged | 25 of 240 scored |

So on this slice the screen catches 4 of 7 late failures and raises 21 other
flags. That is a measured property of this synthetic slice with this bundle, not
a validated performance figure — the sample is 240 of 2 400 test components, far
too small to quote a recall number from. It is recorded because the previous
behaviour hid it entirely.

Worth noting for the demo: **every one of the 7 had `predicted_to_cross_limit:
false`.** All four catches came from the anomaly detector; the forecast
contributed nothing on these components. Raised with Karthik.

### What the MLCC tests actually verify (real artifact, no doubles)

- Every component in the demo slice scores; evidence fields are populated.
- `percent_change` from the real core matches `(latest − initial) / initial`.
- **Cutoff discipline:** setting every 168 h reading to 999.0, or removing all
  post-24 h rows, leaves scores, forecasts, intervals and peer z-scores
  identical. Only the evaluation-only section changes.
- **Determinism:** repeated identical uploads agree exactly.
- **Identity joins:** reversing row order changes nothing per component.
- **No fitting during a request:** `fit` is replaced with a raising stub on the
  detector and all five models, and screening still succeeds. The core's own
  `model_fitted_during_request: false` is asserted separately.
- **Checksum gate:** appending one byte to `xgboost.json` makes `/health/ready`
  return 503.
- Lower limits are rejected (422), not screened against the upper side.
- A renamed `component_family` scores nothing.
- Mixed part profiles inside one batch are rejected by the core; the API returns
  422 with `row: null` rather than inventing a row number.
- Unknown `profile_id` across a batch → unscored, never guessed.
- Peer group size is exposed, and shrinking a batch demonstrably changes both
  `sample_size` and `current_batch_robust_z`.

### Honesty rules enforced in code, with tests

1. **`decision_counts` counts scored records only.** The core folds unscored
   records into `RETEST`; surfacing that verbatim would read as "these parts need
   a retest" when they were never screened. Unscored stays separately visible
   with an `UNSCORED_RECORDS_PRESENT` warning.
2. **The forecast model is read from the response**, never hard-coded. Requesting
   `xgboost` (which lost internal validation to `persistence`) produces
   `selection_warning` plus a `FORECAST_MODEL_NOT_VALIDATION_WINNER` warning
   saying explicitly that this is *not* evidence the chosen model is better.
3. **The XGBoost candidate is named separately.** When `persistence` is active,
   `xgboost_candidate_final_value` is still returned and its explanation carries
   `is_active_forecast: false`, so contributions are never read as explaining a
   number they did not produce.
4. **Observed vs latent stay apart.** `future_outcomes` → `kind:
   "observed_readings"`; simulator labels → `kind: "simulation_truth"`, which is
   never presented as sensor data.
5. **Extrapolation is disclosed.** On the 240-component sample, **61** records
   carry `out_of_training_range_features`, and the response warns that interval
   coverage does not transfer for them.

## 5b. Browser access and the separate outcome file

### CORS (`SIH_CORS_ALLOW_ORIGINS`)

Comma-separated origins, default `http://localhost:5173,http://127.0.0.1:5173`,
empty string disables CORS. Credentials are never enabled; methods are limited
to `GET, POST, OPTIONS`; `x-request-id` is exposed so browser JS can read it.

`pydantic-settings` JSON-decodes complex types before validators run, so the
field is annotated `NoDecode` for a plain comma-separated env value to work.

### Optional `outcome_file`

`POST /api/v1/screen` now takes an optional second CSV of post-cutoff
observations. Single-file requests are untouched, including an empty multipart
part (which a browser sends for an untouched file input).

Design points that matter:

* **Limits can only come from the early file.** `ingest_outcome_csv` *drops*
  `upper_limit`/`lower_limit` if present and warns `OUTCOME_LIMITS_IGNORED`. A
  test sets the outcome file's limit to 99999 — which would hide every crossing
  — and asserts the reported limits are unchanged.
* **Unknown identities are rejected, not dropped.** The core inner-joins outcome
  rows against scored records, so pairing the wrong files would quietly reveal
  nothing. The API checks membership first and returns 422 naming the ids.
* Rejected: rows at or before the cutoff, duplicate identity+hour (within the
  file *and* across both files), unit mismatch, non-finite values, missing
  columns, binary payloads.
* Partial coverage is allowed with an `OUTCOME_COVERAGE_PARTIAL` warning saying
  that an unrevealed component is not the same as one that stayed in limit.

**Invariance proven by test:** adding an outcome file, and separately setting
*every* outcome value to 999.0, leaves recommendations, anomaly scores,
forecasts, intervals, peer z-scores and limits bit-identical. Only the
evaluation section moves.

Real saved examples: `docs/backend/sample_response.json` (no outcome file) and
`docs/backend/sample_response_with_outcomes.json` (with one, 240 outcomes,
7 crossings). Both are genuine runs.

## 7. Limitations

- **Synthetic throughout.** Models and demo data are synthetic. No measured MLCC
  hardware data exists. Nothing here is evidence of aerospace screening accuracy.
- **XGBoost is not the best model here.** Persistence beat it on internal
  validation (0.1795 vs 0.2183 normalized MAE). The demo may select XGBoost, but
  the response says so.
- **Nominal ≠ achieved coverage.** The 0.9 interval is nominal. The manifest's
  own note says device dependence within batches limits exchangeability.
- **Peer scores depend on the uploaded batch.** Screening a component with fewer
  peers changes its robust z. Group size is exposed for that reason.
- **One profile only.** `MLCC_X7R` / `leakage_ua` in µA, at exactly 0 h and 24 h.
- **Python 3.13 vs the 3.12 lock** (§3).
- 800-component runs take ~5.8 s (§4).
